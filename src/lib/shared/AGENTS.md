# Shared lib notes

- Public verification (`/verify?id=`, ENS- certificates and ENB- badges) uses pure rules in `certificateVerify.ts` (verified/valid, revoked, preview, not found, unavailable when records can't be read); records come only from locally issued credentials, never inferred. Why: verification must only confirm credentials actually issued.
- Shareable certificate links (`/certificate/$token`, rules in `src/lib/learner/certificateShare.ts`) carry only holder name, date and style; course, creator and ID always come from the catalogue, and "Verified" shows only when this device issued it to that name. Why: a link must not be able to forge course details or claim verification it can't prove.
- The creator's certificate design (`certificate.design`, incl. `learnerCanChange`) is what learners see first and what issued certificates use; catalogue courses carry their creators' choices in `src/lib/learner/certificateStyles.ts`. Creator-issued certificates (`src/lib/creator/verification.ts`) are also verifiable. Why: one style decision per course, applied everywhere a certificate appears.
- Certificate downloads (PNG, or print-ready A4 PDF built by `certificatePdf.ts` from the same on-screen art) go through `useCertificateExport` (`src/components/shared/certificate/CertificateViewer.tsx`): mouse users save at once; touch screens prepare the PNG first, then a Save/Share sheet saves it on a fresh tap. Full-screen viewing and the phone floating preview reuse the same art. Why: browsers drop the save permission after slow image work on phones.
- Public certificate pages share `certificate/PublicShell.tsx` (hero, optional art and fact chips, footer); only verifiable facts go in its chips. Why: one premium public frame without overclaiming.
- Hand-issued certificates, badge awards, custom badges and name corrections live in one device-wide registry (`credentials.ts`) keyed by recipient email; revocation keeps the record, and approved name corrections keep the ID and list earlier names. Why: learners on the same device receive what creators issue, and history is never rewritten.
- Badges come from `badges.ts` (category decides the emblem shape) and render only through `components/shared/badges/BadgeEmblem` with literal hex so PNG export matches; automatic badges are never hand-awarded. Why: one premium badge look everywhere and no unearned awards.
- Certificates snapshot the printed name (`recipientName`) when issued; later display/certificate-name edits only affect future certificates. Why: historical certificates must stay as issued.
- Names live in one device-wide identity record per email (`identity.ts`: account, display, certificate name + joined role); role stores overlay it on load and keep their legacy name fields synced, and every role's settings edits them through `components/shared/NameSettings`. Why: one name change shows everywhere without rewriting role data.
- Certificate orientation is derived from the template (`layoutOf`/`templatesFor` in `certificate.ts`; portrait = the formal portrait template), not a separate design field. Why: saved designs and issued certificates keep working with no migration.
- Verification wording only reports what a record says ("Record found", "matches an Enski record"), never a stronger claim. Why: records are simulated; nothing outside Enski is checked.
